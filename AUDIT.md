# Проверка синхронизации Studio 0.3.0

Проверены планировщик, исполнитель, восстановление, контроллер, локальный файловый адаптер, внешний импорт, Drive OAuth/public, Яндекс Диск и GitHub. Это проверка исходников и воспроизводимых сценариев на моделях API с настоящими временными файлами. Живые аккаунты, реальный OAuth grant, Shared Drives и файловый наблюдатель запущенного Obsidian здесь не испытаны.

## Исправленные ошибки

| Проблема в 0.2.1 | Изменение и проверка |
|---|---|
| Каждый источник проверял коллизии отдельно. `A/x.md` и `a/y.md` на разных сторонах могли попасть в несовместимую структуру | Общая проверка путей, промежуточных и пустых папок, регистра, Unicode и столкновения файла с папкой до построения и выполнения плана |
| Категории и защищённые пути можно было обойти разным регистром `.OBSIDIAN` | Классификация настроек и защита служебных путей учитывают регистр нечувствительно; добавлен тест |
| Внешняя папка обходилась без исключений; ссылка/коллизия вне scope останавливала импорт | Правила применяются перед обходом; тест с исключённой папкой, ссылкой и коллизией |
| GitHub проверял submodule/symlink до исключений | Исключённый объект больше не обрывает получение; объект внутри scope по-прежнему явно отклоняется |
| Drive мог писать в перемещённую папку по старому ID | Путь разрешается заново по цепочке родителей, проверяются ожидаемый ID, однозначность имени и доступность корня |
| Большие файлы отправлялись одним multipart-запросом | Для файлов больше 5 MiB — последовательные блоки 8 MiB, подтверждённый Range, проверка состояния сессии после потерянного ответа. Нет повторного POST создания файла при неизвестном исходе PUT |
| Загруженные заметки имели общий MIME type | MIME определяется по расширению, например Markdown/Canvas/JSON |
| Изменение только mtime после выбора «новейшего» не отменяло план | Повторная проверка учитывает hash, version, ID, размер и mtime |
| При переименовании удаление старого пути могло предшествовать копированию нового | Переносы выполняются до удалений. Тест отказа записи подтверждает сохранение старого файла |
| Повторное применение старого плана после сбоя могло перезаписать pending-операцию | До повторного выполнения требуется перепроверка и восстановление |
| Сужение scope при незавершённой операции могло представить скрытый файл как отсутствующий | Восстановление требует вернуть путь и лимит в область управления; pending сохраняется |
| Ошибка исполнения возвращалась результатом, не исключением, поэтому счётчик ошибок расписания не рос | Неуспешный результат исполнения учитывается при расчёте задержки повторного запуска |
| Яндекс мог принять upload с HTTP 202, но ещё возвращать старые метаданные | Ограниченное ожидание ожидаемого hash без повторной загрузки; после тайм-аута pending остаётся для восстановления |

## Два разных режима удаления

Старый режим сохранён по умолчанию: **Отслеживать изменения и подтверждённые удаления**. Файл удаляется на принимающей стороне, если история подтверждает его прежнее существование в источнике. Неизвестные файлы назначения сохраняются. «Удаление игнорировать» не стирает историю: включение удалений позже может применить их.

Добавлено явно выбираемое **Зеркало** для одного направления. Источник определяет содержимое: отличающиеся файлы заменяются, лишние файлы назначения удаляются уже на первом запуске, если удаления разрешены. При `ignore` лишние файлы сохраняются. Обычные политики конфликтов в зеркале не применяются. Исключения и лимит размера действуют и в зеркале. План показывает удаления; автоматический запуск с включённым подтверждением оставляет их на просмотр.

Зеркало не устраняет коллизию файла и папки автоматически. Для такой смены структуры требуется переименование/исключение; это предотвращает неявное рекурсивное удаление каталога с неуправляемыми файлами.

## Drive и Sync Engine

Изучен upstream [hesprs/sync-engine, commit d91199e](https://github.com/hesprs/sync-engine/tree/d91199e079f2010bcb4bc9e0dfca7a9e4a2fd10f), прежде всего [fs.ts](https://github.com/hesprs/sync-engine/blob/d91199e079f2010bcb4bc9e0dfca7a9e4a2fd10f/packages/gdrive/src/gdrive/fs.ts) и [upload.ts](https://github.com/hesprs/sync-engine/blob/d91199e079f2010bcb4bc9e0dfca7a9e4a2fd10f/packages/gdrive/src/gdrive/upload.ts).

Адаптированы подходы: свежий поиск по цепочке пути перед операцией, MIME по расширению, последовательная загрузка через resumable session, выбор новейшего одноимённого файла. Это собственная реализация под порты Studio; весь SDK и UI upstream не подключались.

Выбор дублей сделан отдельной настройкой **«Получать новейший дубль (по Sync Engine)»**. По умолчанию коллизия остаётся ошибкой. Включение разрешает только получение, выводит предупреждение с выбранным ID и не удаляет другие копии. При равном времени выбор стабилен по ID. Неоднозначные папки, регистр и Unicode не объединяются автоматически.

Обход всех видимых файлов аккаунта, используемый upstream, здесь не перенесён: Studio работает с произвольной выбранной папкой и полным OAuth scope. Сохранён постраничный обход её поддерева. Это уменьшает охват запроса, но уступает общему индексу по числу запросов на большие деревья.

Обработка частичных подтверждений следует [официальному протоколу Drive](https://developers.google.com/workspace/drive/api/guides/manage-uploads): следующий offset определяется по Range, после потери ответа запрашивается состояние той же сессии. Начало сессии не повторяется автоматически; после перезапуска плагина требуется новый обход. Сессия между перезапусками не сохраняется.

## Что подходит из FreeFileSync

| Подход | Решение для Studio |
|---|---|
| Разделение Two way, Mirror и Update; база предыдущего состояния | Сохраняем собственный baseline для отслеживаемой синхронизации; добавляем отдельное зеркало. Режим Studio с игнорированием удалений не объявляется точной копией Update |
| Сравнение по содержимому отдельно от времени | SHA-256 остаётся критерием равенства. Время используется только при явном выборе «новейшего» |
| Определение перемещений по стабильным ID | Пока используем «копировать, затем удалить». Для оптимизации нужны устойчивые идентификаторы на обеих сторонах и восстановление незавершённого move |
| Versioning для заменяемых и удаляемых объектов | Копии перед заменой уже есть. Нужны интерфейс восстановления и лимиты хранения. Окончательное удаление сейчас отдельной копии не создаёт |

Основания: [режимы и перемещения](https://freefilesync.org/manual.php?topic=synchronization-settings), [сравнение](https://freefilesync.org/manual.php?topic=comparison-settings), [versioning](https://freefilesync.org/manual.php?topic=versioning). Использованы концепции и документация; исходный код FreeFileSync не переносился.

## Реальная готовность источников

| Источник | Реализовано и проверено на моделях | Оставшиеся ограничения |
|---|---|---|
| Drive OAuth | Произвольный корень, вложенные папки, пагинация, SHA-256/скачивание с проверкой версии, pull/push/both, trash/permanent, обновление токена, multipart и resumable | Нет живой проверки ETag/If-Match, Shared Drives и конкурентного клиента; без ETag перезапись/удаление запрещены. Нет changes feed и сохранённых upload-сессий |
| Публичный Drive | Получение через API key; запрет записи, resource key выбранной папки | Не анонимный HTML-скрейпинг. Не всякая ссылка «доступ по ссылке» гарантирует возможность перечисления папки API; нужен тест конкретной папки |
| Яндекс Диск | Корень `disk:/`, постраничный обход, SHA-256, pull/push/both, создание родителей, подписанные URL, trash/permanent и ожидание асинхронного удаления | Токен вводится вручную. Нет атомарного compare-and-swap. Время загруженного файла назначает сервер, поэтому «новейший» сравнивает часы сервисов, а не надёжную причинность изменений |
| GitHub | Получение из коммита, выбранного веткой/тегом; подкаталог; проверка Git blob SHA и SHA-256 | Нет push, LFS, symlinks/submodules внутри scope. Усечённое дерево останавливает запуск. Файловое время отсутствует: при различии политика «новейший» требует ручного решения |
| Vault | Чтение скрытых настроек, содержимое, атомарная замена файла, локальная корзина, проверки ссылок | Desktop. Нет блокировки между процессами; остаётся небольшое окно между последней проверкой и файловой операцией. Поведение редактора и watcher нужно испытать в Obsidian |
| Внешняя папка | Чтение, scope и исключения, проверка изменения во время чтения | Только источник, без записи; активные symlinks запрещены |

## Что ещё не реализовано

1. **Пакетное обновление плагинов.** Категория кода видна, но операции блокируются. Нужны проверка релиза, staging всей версии, выключение/включение плагина и откат; замена отдельных JS-файлов не решает эту задачу.
2. **Пустые папки как синхронизируемые объекты.** Они учитываются для обнаружения коллизий, но не создаются/удаляются отдельно. Нет атомарной смены типа «файл ↔ каталог».
3. **Масштабирование.** Полные повторные обходы, в том числе перед удалениями; нет changes feed, общего индекса, потокового чтения файлов или общего ограничения памяти. Даже resumable upload держит исходный файл в памяти.
4. **Автоматическое трёхстороннее слияние текста.** Есть выбор сторон и конфликтная копия; редактирование общего Markdown-предка отсутствует.
5. **Управление версиями.** Нет очистки по сроку/объёму и UI восстановления. Служебные копии могут занимать много места.
6. **Мобильная версия и системная фоновая служба.** Автоматизация действует только при работающем desktop Obsidian. События vault не гарантируют уведомление о внешней записи скрытых конфигурационных файлов; интервал остаётся необходимым.
7. **Согласование нескольких процессов/устройств.** Локальный baseline не является глобальной блокировкой. ETag и проверки версий уменьшают гонки, но не обеспечивают транзакцию всего vault; создание одинаковых имён двумя клиентами Drive всё ещё может породить дубль.

Приоритет следующего этапа: живые интеграционные испытания Drive conditional writes и Яндекса → восстановление/retention → инкрементальный индекс → пакетное обновление плагинов. Расширение GitHub до записи требует отдельного транзакционного адаптера коммитов.

## Воспроизведение проверок

Проверка 0.3.0: 98 тестов (82 ядро/адаптеры/транспорт и 16 DOM-сценариев).

`npm ci && npm run verify`: тесты ядра/адаптеров/транспорта, DOM-интеграционные сценарии, TypeScript, готовый bundle. Новые сценарии находятся в `test/audit.test.ts` и `test/lifecycle.test.ts`. Модели возвращают потерянные ответы, неполные Range, коллизии, перемещения, ошибки записи, исключённые пути и незавершённые операции; они проверяют решение и фактические побочные эффекты.
