# Независимое ядро Sync Studio

## Происхождение

Из предоставленного архива не извлекались и не читались `main.ts`, `src/ui/**`, `styles.css`, профили/миграции и внутренние планировщики. После просмотра списка файлов были извлечены только auth, выбранные provider-файлы, контракт источника и приложенная лицензия. Существующие UI, настройки, профили, стратегии обхода vault, старые планировщики конфликтов и старые журналы в проект не переносились.

В рабочий код скопированы только `src/auth/google-auth.ts` и `src/adapters/google-desktop-oauth.ts`. Остальные файлы написаны заново, включая совместимые небольшие порты для изолированной аутентификации. Изученные provider-файлы использовались для понимания протоколов; старые координаторы и проекции не подключены.

## Архитектурные ориентиры

- Sync Engine: разделение файловых адаптеров, определения действий и выполнения; независимые local/remote идентификаторы и сохранённое соответствие. https://sync.consensia.cc/deep-dive/sync ; https://sync.consensia.cc/development/file-system
- Syncthing: содержимое и версия — разные сущности; безопасная временная запись перед заменой; явные конфликты имён и удаления. https://docs.syncthing.net/users/syncing.html
- Общепринятая модель синхронизации двух реплик: сравнение `(local, remote, last-confirmed-pair)`, а не только двух текущих файлов; оптимистическая проверка перед записью; персистентное намерение перед побочным эффектом; подтверждение после него.

Это самостоятельная реализация указанных принципов, **не встраивание готового Sync Engine и не утверждение о равной зрелости**. SDK upstream не включён в зависимости. Из Sync Engine намеренно не перенесены ordered glob UI, глобальная конфигурация вместо профилей и допущение «равный размер при первом подключении означает одинаковое содержимое», описанное в его документации. Новое ядро требует сильный хеш. Полного трёхстороннего слияния текста нет: сравниваются состояния для выбора операции.

## Слои

1. `core/model.ts`: типы профиля, endpoint-снимка, подтверждённой пары, операции и результата.
2. `core/paths.ts`: переносимые пути, категории и независимые от порядка исключения.
3. `core/planner.ts`: чистое принятие решений. Не знает Obsidian, HTTP или хранилище состояния.
4. `core/executor.ts`: применяет неизменяемый просмотренный план через Store; проверяет содержимое/версии; не скрывает частичное выполнение под «успехом».
5. `core/recovery.ts`: чистая реконструкция результата прерванной операции. Сохраняет именно подтверждённую пару, не текущее состояние мира.
6. `adapters/state-file.ts`: новый атомарный файл состояния с checksum, последовательной записью, fsync и rename.
7. `adapters/local.ts`: новый адаптер Obsidian. Обходит DataAdapter для доступа и к скрытой конфигурации; события приложения используются как повод перепроверить данные, не как доказательство версии. Для замены — временный файл; для локального удаления обычных файлов — API Vault trash/delete.
8. `sources/remotes.ts`: новые адаптеры Drive/Яндекс/GitHub под единым Store.
9. `controller.ts`: связывает зависимости, аккаунты, расписание и UI. Все операции одного экземпляра плагина сериализованы.
10. `ui.ts`: новый интерфейс по согласованной композиции. DOM строится через API Obsidian, текст не вставляется как исполняемый HTML.

## Инварианты

- Хеш содержимого не зависит от времени, размера или ID провайдера.
- Версия/ID провайдера служит для повторной проверки, но не заменяет сравнение содержимого разных систем.
- До полного списка файлов нет плана удалений.
- Неизвестный локальный файл при получении не является объектом удаления.
- Изменение scope не создаёт удаление.
- Игнорирование удаления сохраняет достаточно истории для последующего применения новой настройки.
- Решённое расхождение не повторяется при той же паре и политике. При смене политики решение пересматривается.
- Режим получения не записывает в удалённый источник; внешний импорт не записывает в исходную папку.
- Перед удалением дополнительно проверяется отсутствие файла на другой стороне.
- До записи побочного эффекта фиксируется намерение. После записи фиксируется полученная пара; затем обновляется baseline и очищается pending.
- Неудачный checkpoint останавливает следующие операции.
- Recovery никогда не принимает позднейшее изменение источника за результат прерванной операции.
- Неоднозначный исход операции останавливает автоматическую запись.
- Секреты не входят в профиль, состояние синхронизации или отчёт.

## Осознанные границы

Нет обещания «exactly once» поверх произвольного облачного API. Используется сохранённое намерение и проверка наблюдаемого результата. Создание файла после потерянного ответа распознаётся при новом обходе по пути и содержимому; дубликаты имён Drive блокируют план. Для операций без серверного conditional write остаётся окно внешней гонки, явно описанное в README.

Обход пока полный и последовательный. Ускорение через событийный индекс, кэш метаданных и инкрементальный changes feed будет отдельным этапом после интеграционных испытаний. Кэш известных криптографических хешей привязан к неизменяемой версии объекта; список удалений не строится из кэша.

Транзакции не охватывают весь vault: уже подтверждённые операции остаются выполненными при остановке следующей. Пакетная установка кода плагинов требует другой единицы транзакции и поэтому сейчас заблокирована. Синхронизация нескольких устройств не превращает этот локальный baseline в глобальный causality graph.
