# W1: сохранение результатов и отмена — первый этап

Дата проверки: 2026-10-16. База: `3c4da8b02c730d865077d7db6b78133c7a58540a` (runtime `a5a4d16`). Это частичная реализация W1, не завершение overhaul.

## Реализовано

- Отказ от общего подтверждения возвращает cancelled с существующей статистикой; per-job host не продолжает Drive-фазу этого задания.
- Отмена подготовки возвращается через runOwnedSession/runSession в runAutoSession. Scheduler не получает retry/finishing для этого результата.
- Подтверждённые счётчики задания сохраняются при исключении последующей стадии: JobBatch предоставляет принадлежащий ему progress объект host executor. Ошибка одного задания не отменяет независимое задание.
- Ошибка без failed item counters больше не превращается в success при проекции карточки: обе точки используют accountedOutcome.
- Ошибки финального сохранения очереди, настроек и журнала возвращают error с сохранёнными подтверждёнными счётчиками. Ошибка settings-save попадает в журнал до его публикации; journal-save блокирует автоматический повтор как shared failure.
- VAM обязателен: legacy vamSoftMode не даёт допуска и не отображается как активный обход. Отзыв допуска отменяет session controller и оба coordinator-пути. Это не доказывает физическую остановку уже отправленного удалённого запроса; normal recovery остаётся обязательным.

## Проверка

`npm run verify`: 546/546 tests, TypeScript, стили, production bundle. Проверки транспорта и OAuth запускаются с разрешением локального HTTP listener; без него sandbox возвращает EPERM. `git diff --check` чистый.

Добавлено 12 тестов; четыре прежних сценария отказа от preview обновлены под явный cancelled вместо null. Восемь новых session-results и два новых drive-host сценария запущены на прежнем runtime: все десять падают на проверяемом поведении. Прежние 19 drive-host сценариев на этой базе проходят. После изменений все новые сценарии проходят. Тест progress API отдельно проверяет сохранение счётчиков при позднем исключении и завершение независимого задания.

Связь с приёмкой: B01/B02 покрыты host-сценариями; B04 покрыт на границе JobBatch/host и финального сохранения, но не доказывает полноту всех внутренних Drive stages. B05 покрыт только сохранением возвращаемого результата при journal failure; durable reconstruction после restart ещё не реализован. VAM bypass/revocation — часть R13.2, не весь readiness lifecycle.

## Открытые границы

- Девять исходов и отдельные admission/accounting/effect-certainty поля ещё не внедрены; legacy admission guards и отсутствие работы могут вернуть null.
- Нет durable accounting-required reconstruction, единого request/run/cycle ID и полной идемпотентной агрегации receipts.
- Внутреннее исключение DriveCoordinator до возврата его статистики ещё может терять локальные счётчики этого вызова. Исправление границы JobBatch не заменяет receipts внутри engine.
- Время последней успешной передачи и счётчик настроек могут сохраниться раньше последующего отказа журнала; атомарной транзакции между ними пока нет. Результат вызова при этом error, подтверждённые эффекты сохраняются.
- Классификация ошибок по тексту, общий retry budget, область блокировок и ручное снятие блокировок ещё требуют отдельной реализации.
- Полное VAM readiness/deadline/late adoption и прекращение всех физических callbacks ещё не доказаны.
- Остальные W2–W4, параллельные transfers, индекс Drive, миграция хранилищ, GC и новая модель конфликтов этим этапом не реализованы.

Live Google Drive и настоящий Obsidian в этом этапе не запускались. Сборка не является подтверждением live protocol/concurrency gates и не открывает existing-ID overwrite.

## Второй этап W1: классификация ошибок (2026-10-16)

- `syncIssue` больше не выводит local-changed/path-collision/retryable из слов диагностического сообщения. Неизвестное исключение получает internal-error, session scope и job domain: останавливается это задание, а не все источники.
- StalePlanError и проверки актуальности локальных bytes в conflict/coordinator/durable mutations выдают явный local-changed. Ошибка создания каталога имеет mkdir-failed; состояние «родитель является файлом» по-прежнему отдельно доказывается через stat и выдаёт path-collision.
- Typed file-scoped IO больше не повышается до session error в DriveCoordinator и при приёме peer artifacts. Независимый файл продолжает работу. Это не превращает любое неизвестное исключение адаптера в безопасный item-local сбой.
- Checkpoint failures на границе сохранения и compaction явно классифицируются как shared checkpoint failures. Реальный Coordinator/JobBatch тест подтверждает блокировку следующего писателя; подтверждённые эффекты не ставятся повторно в очередь.
- Добавлено 11 тестов; все 11 воспроизводят дефекты на `294c62e` и проходят после изменения. Полный `npm run verify`: 557/557, TypeScript, стили и production build. `git diff --check` чистый.

Это реализует B06 и часть item/shared isolation R10.2; полная нормализация IO на всех provider/host границах, error effect certainty, account-level blockers и общий retry budget ещё открыты. Generic exceptions могут останавливать больше работы внутри одного задания, чем специально классифицированные ошибки; это преднамеренный предел достоверности, а не обещание полной изоляции всех ошибок.

## Третий этап W1: бюджеты отправок и восстановимая публикация отчёта (2026-10-16)

### Действующие гарантии

- `SendBudget` сериализует расход одного request step до физической отправки. До пяти sends; конкурентные потребители не могут перерасходовать лимит. Ошибка сохранения бюджета блокирует dispatch и последующие обращения к этому экземпляру.
- NetLayer и GoogleAuthorizedTransport передают один budget через сетевые retries и 401 replay. Вложенный transport не получает независимые пять попыток. Caller может сохранить этот экземпляр для следующего вызова того же step.
- Resumable upload хранит `sendAttempts` в существующем DriveUploadState для chunk(offset,length) и probe(offset). Счётчики checkpoint-ятся перед запросом и проходят верификацию DriveStateStore. Продвижение offset открывает другой step; файл из более чем пяти advancing steps не ограничен пятью запросами на весь файл. Перезапуск не обнуляет сохранённые расходы.
- FileJournal имеет один постоянный `.pending` файл рядом с журналом. Готовая сводка сохраняется и проверяется чтением до публикации кольца. После успешной публикации pending становится JSON null. Новых файлов на каждую сессию не создаётся.
- Повтор публикации использует journalId и не дублирует сводку. load/recover восстанавливают публикацию без вызова sync engine; runOwnedSession проверяет незавершённую публикацию до новых эффектов. Нечитаемый pending блокирует новую сессию, не удаляется молча.
- append/load/recover/clear сериализованы. Clear имеет собственный durable intent; потерянное подтверждение clear не возвращает старые записи после restart. Проверяется запись как pending, так и самого журнала.

### Проверка и границы

18 новых тестов: transport+401 общий предел, параллельные потребители, отмена, отказ persistence, восстановление бюджета, restart chunk/probe, восемь advancing upload steps, проверенный Drive checkpoint/reopen, падение записи журнала/ack, повторная публикация, clear/restart, конкуренция append/clear, повреждение pending и host admission. Полный набор: 575 тестов. Эти проверки используют реальные классы и injected network/filesystem ports; live Drive/Obsidian не проверялись.

**R10.8 и B05 ещё не закрыты полностью.** Общего persisted cycle/job/pair/intent/step registry и его подключения ко всем scheduler continuations пока нет. NetLayer по умолчанию создаёт budget на invocation; новый вызов без переданного budget получает новый экземпляр. Token endpoint refresh — отдельная операция. Upload initialization/metadata effects ещё не имеют этого durable budget. Старые upload states без sendAttempts не содержат достоверной истории отправок.

Для resumable chunk/probe предел сейчас консервативно действует на сохранённый step между перезапусками, а не сбрасывается при новом scheduler cycle. Исчерпание требует дальнейшего явного протокола продолжения; автоматического сброса нет. Старый бинарник schema-v3 может игнорировать новое поле; downgrade не является проверенным сценарием и не доказывает сохранение бюджета.

Восстанавливается **уже сформированная и успешно сохранённая pending-сводка**. Crash между файловым эффектом и созданием сводки всё ещё требует будущей связи runId ↔ operation receipts и реконструкции из ledger. Если запись pending сама не состоялась, восстановление этой сводки не гарантируется. Формат девяти outcomes/accounting-required и межпроцессная блокировка ещё не внедрены. Pending-файл не заменяет ledger и не даёт разрешения повторять неизвестный эффект.
