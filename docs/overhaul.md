# Поэтапный overhaul

Дополнение 2026-10-14: [критическая сверка Drive и V6](audits/drive-jobs-cross-review.md) и [исправленный per-source jobs plan](per-source-jobs-plan.md) уточняют следующие архитектурные этапы. Исторические описания ниже относятся к своему этапу; фактический статус Drive-пилота указан в [руководстве интеграции](google-drive-integration.md).

## Этап 1: защита существующего pipeline

Сохранены текущие режимы `fetch/light/full` и формат пользовательских настроек. Реализован первый этап защиты, а не завершённая новая архитектура.

### Что изменилось

1. В репозитории появились закреплённые зависимости, сборка, строгая проверка типов, тестовый runner и CI. `npm run verify` — единая команда проверки.
2. До построения плана проверяется весь манифест: пути, размеры, версии, дубликаты, регистр, Unicode и конфликты файла с каталогом. Преобразованный локальный манифест проверяется повторно.
3. До записи проверяются размер полученных байтов, включая пустые файлы, и доступный digest: SHA-256, Git blob SHA-1 или CRC32. ETag и weak-токены остаются признаками версии, а не хэшами содержимого.
4. WebDAV использует XML-парсер с проверкой namespace и `propstat/status`. Повреждённый/неполный ответ завершает сессию с ошибкой. Ответ каждой коллекции должен содержать её саму. Отсутствующий optional property с 404 допустим; отсутствие типа ресурса или размера файла — ошибка.
5. WebDAV разрешает href только в пределах origin и корня источника; редиректы запрещены. Для сильного ETag GET получает `If-Match`. Внешняя коллекция не получает запрос с credentials.
6. ZIP открывает новый снимок при каждом `getManifest`; TTL аренды ресурсов больше не подменяет проверку свежести. Повторяющиеся имена записей отклоняются. Raw Git-файл, похожий на JSON-ответ API, больше не декодируется по эвристике.
7. Подтверждение плана предшествует переименованиям. Совпадение хэша больше не используется как доказательство принадлежности пути для переноса. Ошибка переноса завершает сессию до последующих загрузок/удалений.
8. Отмена проверяется после диалога конфликта и перед записью. После ответа перечитывается последняя сохранённая локальная версия. `remote-wins` и `full` сохраняют её копию до замены. Отказ записи копии сохраняет оригинал. Локальные байты повторно проверяются перед заменой; хост может предоставить атомарный compare-and-write.
9. Адаптер Obsidian использует `Vault.process` для замены существующего UTF-8 Markdown-файла с сравнением текущего текста. Для неподдерживаемых файлов остаётся проверка байтов перед обычной записью.
10. Удаления выполняются после загрузок и только при отсутствии их ошибок, отложенных/припаркованных ошибок и отмены. Для каждого удаляемого файла сначала создаётся копия; изменение оригинала во время копирования блокирует удаление. Каталоги рекурсивно не удаляются.
11. Записи кэша исчезнувших удалённых файлов сохраняются до успешного удаления. Retry, отказ от подтверждения и повторная загрузка не стирают базу сравнения или владение неразрешёнными orphan-файлами. Ошибка удаления учитывается в результате и повторяется при следующем ручном зеркале.
12. Записи кэша и checkpoint сериализованы. Сессия держит блокировку до завершения финального сохранения и освобождения ресурсов. Нельзя заменить её source/cache в процессе работы.
13. Вся локальная директория работающего плагина защищена от загрузок, перемещений и зеркальных удалений, включая варианты регистра. Исключения проверяются также для локальной цели mapping и orphan-файлов.
14. Обычная синхронизация уважает backoff и парковку ошибок. Наличие незавершённой очереди не выдаётся за «всё актуально». Заблокированные и отложенные удаления отражаются в результате и журнале; заблокированные удаления видны в ручном preview.

### Временные ограничения

| Источник / операция | Текущее поведение |
| --- | --- |
| Git, ZIP: ручные удаления | Разрешены после подтверждения; содержимое сохраняется копией |
| Drive, Яндекс.Диск, WebDAV: удаления | Заблокированы независимо от ручного подтверждения; требуется доказательство полноты/стабильности обхода |
| Любой источник: auto-удаления | Отложены до появления явного разрешения в новых правилах |
| Ошибка/отложенная загрузка и удаления в одной сессии | Удаления отложены, владение локальными файлами сохранено |
| Восстановительные копии | Видимые `.conflict-*` рядом с файлом; также проверенные скрытые recovery-объекты. Без автоматической очистки |
| Папки | Сохраняются; удаляются только перечисленные файлы |

У существующего результата сессии пока три состояния: `ok/cancelled/error`. Заблокированная/неполная сессия использует `error` с отдельными счётчиками; UI подписывает его «Требует внимания». В новом runner нужны полноценные `partial/blocked` с причинами по операциям.

Копии — обязательное условие **до** замены/удаления; при нехватке места операция завершается ошибкой. Генератор имён прекращает операцию при исчерпании свободных кандидатов вместо удаления старой копии. Этап 2а добавил проверяемые recovery-объекты; атомарного восстановления набора операций и гарантии fsync пока нет.

### Что этот этап не гарантирует

- Сравнение через `Vault.process` защищает сохранённый Markdown-текст. Несохранённые буферы редактора и период активного набора пока не учитываются.
- У бинарной записи, создания нового файла, переименования и удаления остаётся промежуток между последней проверкой и операцией хоста. Копия не доказывает атомарность и не может сохранить правку, поступившую после этой проверки. Нужны новые IO-контракты, защита открытых редакторов и проверка возможностей хоста.
- Legacy-кэш ещё не заменён полностью: новый журнал хранит применённые после обновления операции и восстанавливает их checkpoint, но не подтверждает происхождение старых записей.
- Конфликт с `ask` в фоне пока может открывать диалог. Новые правила должны отправлять такой конфликт в inbox без модального окна.
- Full теперь сверяет фактические байты. Для weak/ETag нужна собственная применённая SHA-256-база; без неё состояние уточняется загрузкой, а не выводится из совпадения токенов версии.
- Не завершены унификация полей конфигурации Drive/WebDAV, безопасная смена source identity, host routing Git, OAuth/доступ Drive, форматирование Google Docs, мобильная распаковка ZIP и provider-specific retry/version handling.
- Сборка не заменяет `manifest.json`, установочный пакет и проверку совместимости настоящего Obsidian. VAM/governance-гейты сохраняются; тестовое окружение не подтверждает их интеграцию с реальным менеджером.

## Этап 2а: план, намерения и восстановление

Введён чистый `createOperationPlan`: он не вызывает файловые или сетевые порты и возвращает замороженные операции и summary. Локальная SHA-256, размер, отсутствие файла, remote locator и ревизия конфигурации фиксируются **до preview**. Downloads, удаления и переносы исполняются с этими условиями; новые байты после подтверждения не получают прежнее разрешение на перезапись. Компиляция проверяет зависимости переносов и запрещает циклические/неоднозначные изменения. Отбор кандидатов пока использует существующие diff, политики и очередь.

Конфигурация сессии копируется: область, mirror-уровень, useTrash, conflict strategy и mapping. Семантическая ревизия сверяется с настройками перед изменением файла; смена credentials также инвалидирует подготовленную сессию. Адаптер пересоздаётся при изменении его полей, даже если legacy source ID остался прежним. Ротация токена сохраняет кэш. Секреты и их fingerprint в журнал не записываются. Общая блокировка плагина теперь охватывает подготовку, auth, исполнение и финализацию журнала; scan проходит через неё и проверяет ревизию.

Перед изменением существующих байтов создаётся content-addressed объект `recovery-v2/<sha256>.bin` в директории плагина. Размер и SHA-256 проверяются чтением, в том числе при повторном использовании объекта. Затем публикуется намерение `committing`; после операции проверяются фактические байты и сохраняется `applied`. При подтверждённом отказе до изменения intent получает `not-applied`; неоднозначная IO-ошибка оставляет намерение для сверки. В записи есть plan ID, namespace, путь, ожидаемые версии, recovery reference и эффект для кэша.

В 2а состояние публиковалось последовательными полными поколениями `sync-operations-v2-<sequence>.json`: checksum payload, проверка схемы, запись временного файла, чтение, rename, повторное чтение. Из committed-поколений сохранялись текущее и предыдущее. Формат заменён в 2б.1, описанном ниже. Повреждённое последнее поколение блокирует работу; отката к более старому или пустому состоянию нет. Незавершённые временные файлы не считаются опубликованными. Неоднозначный результат публикации запрещает дальнейшие записи текущему экземпляру; после перезагрузки плагина новый экземпляр проверяет фактическое состояние диска.

При следующей сессии старое намерение сверяется с vault: ожидаемый результат означает завершённую операцию, исходная версия — неприменённую. Третья версия сохраняется и блокирует продолжение до разбора. Старые команды записи, удаления или переноса автоматически **не повторяются**. Подтверждённые операции восстанавливают legacy checkpoint. Отдельная applied-база хранит собственную SHA-256 локальных байтов, original remote path и confidence: проверенный digest либо наблюдённая версия weak/ETag. Получение входящей конфликтной копии не продвигает applied-базу основного файла.

Full проверяет локальное отклонение даже при неизменившемся remote. Исправлен обход выбранного дочернего поддерева внутри отключённого родителя. Сообщение пустой сессии теперь «Нет новых операций синхронизации»: оно не утверждает равенство исключённых или сохранённых локальных файлов источнику.

### Границы 2а и следующий шаг 2б

- Namespace пока равен legacy source ID. Connection UUID, каноническая identity, principal/generation, отдельная очередь для каждой области и миграция владения ещё нужны. Старые коллизии ID и неоднозначные legacy-записи этот этап не исправляет.
- Бюджеты пока фиксированы: 512 MiB объектов и 10 000 записей операций суммарно по источникам, включая завершённые записи. При исчерпании следующая операция сохраняет оригинал и завершается ошибкой. Recovery-объекты и история не очищаются автоматически. Виден старый `.conflict-*` backup; скрытая копия может занимать дополнительное место.
- В 2а metadata поколения переписывали накопленное состояние при каждом переходе. На in-memory портах 100 записей новых однобайтовых файлов дали 3 469 279 записанных байт (~196 ms), 500 — 86 217 281 байт (~2968 ms). Эту стоимость перезаписи устранил этап 2б.1. Замеры не включают чтения, настоящий диск или сеть.
- Нет полного staging всего batch до первых изменений: проверенная независимая загрузка может завершиться до ошибки другой. Удаления при такой ошибке блокируются. Нет атомарности всей сессии, power-loss/fsync гарантии, межпроцессной блокировки или синхронизации нескольких устройств, редактирующих директорию плагина.
- UI восстановления/разбора `blocked`, retention, защита dirty-редакторов, новые IO-контракты для binary/rename/delete и типизированные причины partial/blocked остаются незавершёнными. Повреждение журнала и третья версия после сбоя требуют отдельного review, а не автоматического уничтожения истории.

Этап 2б включает хранение и масштабирование, версионирование источника/области и очереди, recovery UI и staging. В 2б.1 закрыта перезапись всего состояния на каждой операции; остальные части ещё нужны. Только после них включается новая семантика режимов с миграцией. Текущие `fetch/light/full` сохранены; новые фоновые разрешения не выданы.

## Этап 2б.1: журнал небольших записей и компактация

`OperationStore` публикует отдельные immutable-файлы `sync-operations-v3-event-<sequence>.json` для `begin` и `finish`. В payload есть последовательный номер, checksum предыдущей записи и команда. Запись по-прежнему проходит временный файл, проверку чтением, rename и повторное чтение с ожидаемым checksum. В памяти изменяется только нужная запись и её applied-база; полное состояние не клонируется и не сериализуется на каждом переходе.

Полные `sync-operations-v3-checkpoint-<sequence>.json` появляются адаптивно: перед новым намерением, если после checkpoint накопилось не менее `max(256, число операций в истории)` событий. Checkpoint включает все операции, статусы, recovery-ссылки, applied-базы и tip цепочки. Обслуживание выполняется перед новой операцией; уже применённый файл не получает ложную ошибку загрузки из-за последующей автоматической компактации. `compact()` позволяет отдельно завершить компактацию метаданных.

Загрузка проверяет последний checkpoint и replay-хвост: схему, checksum, последовательность номеров, predecessor и допустимые переходы статусов. Если сохранён event на номере checkpoint, его checksum обязан совпадать с tip. `applied` и `not-applied` — терминальные состояния. Разрыв хвоста, повреждение последнего checkpoint или отсутствие migration marker не превращаются в пустую историю и не вызывают автоматический fallback.

После проверенной публикации сохраняются последний и предыдущий checkpoints и все события после предыдущего. Удаляются только заменённые metadata-файлы. Для границы очистки проверяется также предыдущий checkpoint; неожиданное будущее поколение не даёт разрешения удалять историю. Прерванная очистка может повториться. Логические записи операций и recovery-объекты не удаляются, поэтому остаются восстановление, проекция legacy-кэша, различие incoming/applied и защита от повторного использования operation ID.

Миграция с 2а выполняется перед первой новой записью. Обычная загрузка legacy-состояния остаётся read-only. Последнее поколение v2 проверяется, затем публикуются начальный checkpoint v3 и `sync-operations-v2-migrated.json`; только после этого разрешены новые events. Исходные v2-файлы сохраняются без изменений. Marker заставляет читатель этапа 2а остановиться на неизвестном формате при откате к той сборке. Это не гарантия для более старых сборок плагина, которые вообще не знают `OperationStore`.

### Замер и остающиеся ограничения

`npm run bench:state`, Node 24.19.0, in-memory порты. Сценарий без applied-эффектов совпадает с замером 2а: новые однобайтовые файлы. Время диагностическое; объём означает только запись metadata, без чтений и байтов vault/recovery.

| Операции | Applied-эффекты | Записано metadata | Время |
| --- | --- | --- | --- |
| 100 | Нет | 87 885 байт | ~74 ms |
| 500 | Нет | 571 366 байт | ~200 ms |
| 5000 | Нет | 7 210 759 байт | ~1893 ms |
| 100 | Да | 107 875 байт | ~42 ms |
| 500 | Да | 883 994 байт | ~183 ms |
| 5000 | Да | 12 709 195 байт | ~1901 ms |

Для 500 операций без applied-эффектов объём записи уменьшился с 86 217 281 до 571 366 байт, примерно в 151 раз. Регрессионный тест требует менее 2 MiB metadata для 500 операций с applied-эффектами и проверяет последующую загрузку всех баз. Дополнительно выполнены публикация, компактация и повторная загрузка в настоящем временном каталоге файловой системы.

- Это компактация файлов журнала, а не retention истории: квоты 10 000 операций и 512 MiB recovery остаются. Все recovery-ссылки сохранены; освобождение квоты требует отдельной политики хранения и UI.
- У каждого события отдельный файл. На замере 5000 операций сохранилось 5907 metadata-файлов. Нужны реальные desktop/mobile измерения каталога и replay; этот benchmark не подтверждает готовность массового onboarding.
- Recovery Store пока перечисляет и проверяет размеры существующих объектов при каждой новой копии. Benchmark новых файлов не измеряет эту стоимость или двойное хранение visible/private backups.
- Исходные поколения v2 и незавершённые временные файлы сохраняются для разбора; автоматического удаления по возрасту нет.
- Смена source identity, очереди по connection/generation, подтверждение их очистки после сбоя, recovery UI, staging и защита несохранённых редакторов остаются следующими частями 2б. Гарантий fsync/power-loss и межпроцессной координации пока нет.

| 5. Auto и UX | Один runner всех триггеров, coalescing, debounce, backoff/jitter, editor-idle, конфликт inbox, onboarding preview | Фоновая работа не показывает модальные окна и не применяет запрещённые разрушительные операции |
| 6. Миграция | Явное преобразование legacy-режимов/политик, обратимая миграция, проверка реального vault | Никакое разрушительное разрешение не расширяется при обновлении; релизные метаданные восстановлены |
| 7. Яндекс.Диск и WebDAV | Проверка стабильности инвентаря, version pinning/preconditions, provider retry и ошибки | Удаления включаются только при доказанных гарантиях adapter contract |
| 8. Drive | Единая конфигурация, OAuth, shared drives/resource keys, явный экспорт Docs и идентичность файлов | Реальные аккаунты/permissions/пагинация и отдельные политики для нестабильных/exported файлов |

Миграция обязательна до включения новой модели для существующих пользователей, независимо от порядка разработки UI и адаптеров.

## Целевая классификация режимов

Режим должен описывать поведение, а не техническую глубину зеркала. Три профиля:

| Профиль | Общие пути | Новые локальные файлы | Исчезнувший remote-файл |
| --- | --- | --- | --- |
| Сохранять локальные правки | Remote применяется, если local соответствует последней применённой базе; иначе конфликт в inbox | Сохраняются | По умолчанию сохраняется |
| Обновлять из источника | Remote заменяет общий путь с восстановительной копией | Сохраняются | По умолчанию сохраняется; удаление — отдельное разрешение |
| Зеркало источника | Выбранная область приводится к source snapshot с восстановительными копиями | Удаляются только в подтверждённой области | Удаляется при доказанной полноте снимка и разрешении |

Второй профиль соответствует запросу «сохранять удалённую версию общих файлов, не удаляя новые локальные». Политика содержимого, удаления, область и разрешения auto — отдельные оси. Эти профили **ещё не реализованы**; переименование legacy-пунктов без новой семантики недопустимо.

## Проверка реализованных этапов

`npm run verify` проверяет типы, регрессионные сценарии и bundle. Тесты используют портовые реализации vault/filesystem/HTTP и настоящие функции сравнения, хэширования, разбора XML и ZIP. Проверяются отмена во время вопроса, изменение после preview/backup, отказ compare-and-write, ошибки удаления, парковка, concurrent flush, задержанная финализация, недоверенные ответы провайдеров, crash до/после изменения файла, corrupt state/recovery, неопределённая публикация, квота, incoming/applied версии и смена credentials.

Проверки на настоящем Obsidian, облаках и мобильном устройстве пока не выполнялись. Их результаты должны быть отдельным критерием допуска к выпуску, а не выводиться из прохождения unit-тестов.
