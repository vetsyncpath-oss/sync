# Google Drive: пилотная интеграция

Состояние на 2026-10-14, сборка `drive-pilot-2026-10-14`. База ветки — `overhaul/2b1-recovered`, commit `d74128619b151af58f4ebdc22e8a61b270e81c8d`.

Это проверяемая реализация первого этапа, предназначенная для испытаний на отдельном vault и отдельной папке Drive. OAuth, executor и интерфейс ещё не проверены в настоящем Obsidian с настоящим Google-аккаунтом. Установочного manifest в репозитории нет; этот checkout не является готовым релизом.

## Что реализовано

| Область | Поведение в этой ветке |
|---|---|
| Авторизация | Desktop OAuth Authorization Code + PKCE S256, системный браузер, временный listener на `127.0.0.1`; внешний сервер не нужен |
| Учётная запись | Проверяется Google `sub`; access token только в памяти, refresh token через Obsidian SecretStorage; в подключении хранится ссылка |
| Папка | Выбор через браузер папок или ссылку/ID; сохраняется фактический Drive ID, включая выбор корня My Drive |
| Совместимость | Старые профили и подключения сохраняют pull-поведение; bidirectional задаётся явно |
| Новые файлы | Начальное объединение папок: новый локальный файл отправляется, новый удалённый скачивается; одинаковые байты принимаются без замены |
| Изменённый удалённый файл | Проверка содержимого и версии после скачивания, затем условная локальная запись; локальные изменения защищены |
| Изменённый существующий локальный файл | Временное ограничение по решению пользователя: локальная версия публикуется `.conflict-drive-local-*` на обеих сторонах; существующий удалённый объект сохраняет ID и содержимое; локальный основной файл получает удалённую версию при доступном guard; остаётся запись о необходимости проверки копии |
| Настоящий конфликт | Различающиеся версии сохраняются обе: удалённая основная и локальная уникальная копия на обеих сторонах. Копии создаются без перезаписи прежних файлов |
| Удаление | Только tracked после согласованного baseline, автоматически через корзину в обе стороны; delete/edit сначала сохраняет изменённую версию на обеих сторонах |
| Повтор передачи | Зарезервированный ID нового объекта и неизменяемый recovery-payload записываются до публикации; resumable URL и подтверждённый сервером offset сохраняются в приватном состоянии |
| Ошибки | Независимые файлы продолжаются после файловой ошибки; повреждение состояния/журнала, утрата корня или авторизации останавливают дальнейшие соответствующие записи |
| Автозапуск | «Только при запуске» сохраняет этот режим в статусе; временная ошибка допускает ограниченные продолжения; после первого успешного прохода или завершившейся передачи назначается сверочный проход |
| Хранилище | Обычно два проверенных checkpoint на namespace; ошибки очистки видны и имеют предел накопления. Пустые failed-очереди не удерживают старые manifest namespace |

Baseline двусторонней синхронизации отделён от pull cache. Его идентичность включает аккаунт, корневой ID и маршруты подключения. Смена токена, поведения профиля или несвязанного провайдера не должна сбрасывать сравнение содержимого. Изменение аккаунта, корня или mapping создаёт другую область состояния без вывода об удалениях.

## Подключение для испытаний

1. Используйте Obsidian desktop **1.11.4+** с SecretStorage. OAuth-подключение не поддерживается на мобильном устройстве; старые источники остаются доступны в пределах их возможностей.
2. В Google Cloud включите **Google Drive API**. В **Google Auth Platform → Data Access → Add or remove scopes** добавьте `https://www.googleapis.com/auth/drive` и `openid`. Ранее выбранный `drive.readonly` недостаточен для нового двустороннего режима. `email` не нужен текущей реализации. `drive.file` не покрывает произвольное содержимое выбранной существующей папки.
3. Создайте OAuth client типа **Desktop app**, скачайте JSON. Для внешнего приложения в Testing добавьте аккаунт в Test users. У такого режима refresh token для Drive обычно истекает через семь дней; потребуется повторный вход. Публичный выпуск с полным Drive scope требует отдельного решения по Google verification.
4. В подключениях плагина выберите Google Drive и desktop OAuth, импортируйте JSON и выполните вход. Выберите удалённую папку. Подключение с публичным API key остаётся отдельным pull-адаптером.
5. В дереве vault явно назначьте этой области подключение и профиль `standard:drive-bidirectional`. Его поведение — изменения, tracked-удаления через корзину, автоматическое сохранение конфликтной версии. Для вложенного Git/ZIP/WebDAV-подключения назначьте отдельный pull-профиль; унаследованный bidirectional для него отклоняется.
6. Сохраните настройки, проверьте область и запустите ручную синхронизацию на тестовых данных. Пока новые удалённые операции не представлены полностью в legacy preview: кнопка запуска выполняет свежую сверку, а не подтверждает исчерпывающий push/trash preview.
7. После ручной проверки включите желаемый режим автосинхронизации. Режим «Только при запуске» не включает постоянное наблюдение за редактированием после завершения стартовой задачи.

Grant разрешает доступ ко всему Drive, но executor ограничивает действия выбранным корнем. Перед изменением объекта повторно проверяется цепочка родительских ID и, где применимо, ожидаемый относительный путь. Это клиентская граница, а не отдельная Google permission на папку; внешние изменения между сетевыми проверками не образуют атомарную транзакцию.

## Режимы и спорные состояния

- `preserve` защищает область от новых операций. Старые `seed`, `safe`, `source`, `conflicts` сохраняют прежние значения; миграция не включает отправку или удаление.
- Новый bidirectional допускает `changes`, `keep`/`tracked`, `keep-both`/`remote-wins`/`ask`. Выбор `local-wins` и legacy `incoming` заблокирован до реализации безопасного обновления существующего Drive ID.
- `ask` в фоне оставляет файл ожидающим решения и не открывает модальное окно. В ручном общем запуске сначала завершаются независимые файлы обоих pipeline, затем предлагаются решения по отдельным конфликтам. Отложенный конфликт не считается полностью успешной синхронизацией и не обновляет `lastSyncTime`.
- Не найденный при перечислении ранее известный файл проверяется по ID. Только подтверждённый `trashed` для объекта внутри выбранного корня позволяет удалить неизменённую локальную версию. HTTP 404, потеря доступа и перемещение за пределы корня оставляют локальный файл и нерешённое состояние.
- Без baseline отсутствующий файл считается новым, а не удалённым. Начальная синхронизация объединяет содержимое. При tracked delete/edit копия должна успешно попасть на обе стороны до удаления исходного пути.
- При `keep` удалённый tracked-объект можно восстановить из Drive trash с тем же ID без перезаписи содержимого; различие версий снова проходит конфликтную проверку.
- `scan` восстанавливает отсутствующие локальные файлы; он не публикует новые файлы в Drive и не воспроизводит ранее запланированное удаление. `force` не отменяет защиту локальных данных и не очищает двусторонние baseline.
- Для обычного текста используются `Vault.process`/`DataAdapter.process`. Обновление существующего бинарного файла блокируется, если host не предоставляет условную замену. Файл сохраняется, ошибка видна, опубликованная конфликтная копия и намерение остаются для повторной проверки.

Ограничение сохранения ID существенно: локальная правка существующего файла пока **не становится автоматически основной удалённой версией**. Её копия доступна на обеих сторонах. Основной файл в vault следует удалённой версии после сохранения копии. В записи review указана копия; запись снимается, когда основной файл на обеих сторонах соответствует сохранённому предложению. Отдельного интерфейса принятия такой копии в основной Drive ID пока нет.

## Состояние, журнал и очистка

Все control-файлы, `.trash` и собственная папка плагина защищены от обычной синхронизации. Состояние записывается с checksum, проверкой опубликованного поколения и сериализацией сохранений. Повреждённый последний checkpoint не заменяется молча более старым или пустым baseline.

Локальный `sync-operations-v3-*` ledger сохраняет незавершённые операции и необходимую историю. Компактация обычно оставляет два checkpoint и опорные event-файлы. При невозможности очистить старые поколения запись ограничивается: для local ledger — до восьми checkpoint, для Drive state — до четырёх. Ошибка очистки делает сессию проблемной. После исправления прав следующие операции снова пытаются выполнить очистку. Неизвестное будущее поколение не удаляется как мусор.

`drive-state-<namespace>-<sequence>.json` содержит baseline, pending, resumable state и review. Полный файл не следует включать в публичные отчёты: upload-session URL даёт доступ к активной передаче. Диагностика не должна печатать токены, callback code или этот URL.

`manifest-<namespace>.json.previous` является резервом используемого cache, а не отдельной версией на каждый проход. Старый namespace и его `.previous`/`.bak`/`.tmp` удаляются, когда его не удерживают действующие маршруты и непустые failed-очереди. Drive baseline namespaces автоматически не удаляются: смена mapping не делает старую историю восстановления мусором. Видимые конфликтные копии остаются пользовательскими файлами.

Окно восстановления может очищать завершённую локальную историю старше 30 дней. При сборе payload учитываются ссылки **всех сохранённых Drive namespaces и retained checkpoint**, а не только активного подключения. Это защищает незавершённые удалённые передачи. Автоматической политики удаления старых Drive baseline/review и интерфейса ручного закрытия всех remote pending ещё нет.

Сессия становится полностью успешной только после сохранения журнала и подтверждённого сохранения настроек, при отсутствии ошибок, очереди и отложенных решений/удалений. Uploaded и удалённые Drive-trash действия отражаются отдельно. Публичный running state охватывает подготовку, оба executor и завершающие сохранения.

## Ограничения и следующий этап

Полная целевая спецификация приведена в [google-drive-bidirectional-spec.md](google-drive-bidirectional-spec.md); статус в этом документе описывает фактическую реализацию.

| Следующая функция | Почему пока не заявляется |
|---|---|
| In-place content update существующего ID | Требуются live-проверки параллельных чужих правок и восстановления ревизий; сейчас включён согласованный conflict-copy gate |
| Перенос rename и tombstone жизненного цикла | Стабильные Drive ID уже есть, но идентичность локального rename и долговременные tombstone не реализованы. Переименование может выглядеть как создание/удаление или неизвестное отсутствие |
| Пустые папки | Создаются только необходимые родители файлов; самостоятельная синхронизация и удаление пустых каталогов не реализованы |
| Changes API, realtime и warm incremental scan | Пока выполняется полное перечисление выбранной папки и локальное хеширование. Листинг не является атомарным snapshot; согласованность при внешних изменениях требует повторной сверки |
| Потоковая передача и multipart small-file path | Сейчас ограниченные ArrayBuffer, последовательный executor и resumable chunks по 8 MiB. Это не скорость и память Sync Engine; default file cap — 64 MiB, настройка 4–256 MiB |
| Shared Drives и resource keys | API-флаги предусмотрены, но создание с заранее выделенными ID, полномочия и link/resource-key сценарии не проверены на аккаунте. Пилотная область — папка My Drive |
| Google Docs/Sheets/Slides, shortcuts | Эти объекты исключены, экспорт и следование shortcut не реализованы |
| Полный bidirectional preview, решение review, remote repair UI | Legacy preview и local recovery не покрывают все новые удалённые намерения |
| OAuth lifecycle polish | Нужны явный revoke и очистка уже сохранённых неиспользуемых credential references; отменённые новые черновики уже очищают свои secrets |
| Производительность | Нет live benchmark и обещания равной Sync Engine скорости; concurrency, Changes и stat/hash cache должны пройти отдельные измерения |

До этих работ пилот нельзя называть полной заменой Sync Engine или готовой двусторонней production-синхронизацией. Откат к pull-профилю прекращает новые push/trash решения, но не отменяет уже опубликованные файлы. Не удаляйте ledger/recovery для «сброса ошибки»: это убирает сведения о незавершённых эффектах. Возврат к старой сборке при remote pending требует отдельной проверки восстановления.

## Проверки

`npm run verify` запускает весь регрессионный набор, TypeScript, стили и production bundle. Автоматические тесты используют временные каталоги и fake API, а desktop callback действительно проверяется через localhost. Среди сценариев:

Финальный прогон этой ветки: **382/382 теста**, TypeScript и production build прошли; `git diff --check` без ошибок. Полный MIT notice проверен в полученном `main.js`. Это результат локальных/fake-API проверок, без live Google/Obsidian.

- Возвращённые и выброшенные 401, конкурентный refresh, потерянный/отозванный grant, отменённый callback и поздний refresh без восстановления credentials.
- Полная пагинация, `incompleteSearch`, alias/case/NFC collisions, корень вне доступа, одинаковый размер с разными байтами, проверка checksum и version.
- Bootstrap union, односторонние изменения, delete/edit, 404 без удаления, сохранение Drive ID и review без повторного создания копии.
- Частичный 308, серверный offset, неизвестный результат создания, возобновление с зарезервированным ID, редактирование во время передачи.
- Ошибки сохранения настроек, checkpoint, очистки и operation acknowledgement; остановка дальнейших опасных записей; защита physical path между namespaces.
- Mixed Git + Drive orchestration: неполный inventory до любых пользовательских записей; независимые файлы до вопросов; корректное слияние результатов.
- Startup-only retry/follow-up, pause/resume, смена режима во время запуска, финальный no-op и отображение текущего состояния.

Перед выпуском нужны live-сценарии на отдельном vault:

1. Реальный вход, повторный запуск Obsidian, отключение сети, повторный вход после истечения grant; проверка отсутствия токенов в `data.json`/логах.
2. Выбор вложенной My Drive папки; соседние папки никогда не меняются. Перемещение объекта наружу и потеря полномочий оставляют локальные данные.
3. Новые Markdown, JSON, вложения и нулевой файл в обе стороны. Несколько страниц списка, одинаковые байты, различающиеся одинакового размера файлы.
4. Локальная правка существующего ID: основной ID/ссылки сохраняются, копия содержит точные локальные байты на обеих сторонах. Проверка бинарного guard и несохранённого редактора.
5. Удаления в обе стороны, delete/edit на обоих направлениях, trash unavailable, смена root/account/mapping без массового удаления.
6. Обрыв upload и закрытие приложения после remote effect, до checkpoint; повторный запуск не создаёт повторный объект. После исправления прав cleanup возвращается к обычному пределу.
7. «Только при запуске»: конфликт не останавливает независимые файлы, transient retry и завершающая сверка происходят автоматически, после завершения периодические проходы не включаются.
8. Внешние правки/rename во время перечисления, скачивания, копирования и trash; измерение числа запросов и памяти на большом тестовом наборе. Отдельные Shared Drive пробы до включения их в поддерживаемую область.

До получения результатов этих проверок content update существующего Drive ID остаётся выключенным.
