# Sync

Плагин Obsidian для синхронизации Git, ZIP, Яндекс.Диска, Google Drive и WebDAV с локальным vault. Существующие подключения и профили работают **из источника в vault**. В этой ветке добавлена пилотная **двусторонняя интеграция Google Drive через desktop OAuth** с выбором удалённой папки. Новый профиль включается явно; обновление плагина не разрешает отправку файлов автоматически.

Настройка, реализованное поведение и обязательные проверки перед выпуском: [Google Drive integration](docs/google-drive-integration.md). Существующие Drive ID сохраняются: новые файлы отправляются обычно, а изменённая локальная версия существующего объекта пока публикуется конфликтной копией на обеих сторонах и требует проверки. Обновление содержимого существующего Drive ID будет отдельным этапом после проверки гонок на реальном аккаунте.

Критическая сверка выявила пробелы пилота: созданные Drive-копии не скачиваются автоматически на другой vault из-за общего name-фильтра, для unknown/review состояний нет полного интерфейса решения, а тёплый no-op переписывает полный Drive state на каждый файл. [Аудит и воспроизведения](docs/audits/drive-jobs-cross-review.md) и [исправленный план независимых jobs](docs/per-source-jobs-plan.md) включены в будущий overhaul. Эта документация не означает, что новый JobManager уже реализован.

Идёт поэтапный overhaul. После защиты существующего pipeline добавлены неизменяемый план, журнал намерений, recovery-объекты и сверка операций после сбоя. Этап 2б.1 заменил перезапись всего журнала небольшими checksum-записями и адаптивными checkpoints с компактацией. Режимы перенесены в профили с назначениями из дерева и выбором источника для каждого файла. UI-overhaul согласовал черновики, область vault, запуск отдельных источников, подробный план и восстановление; сценарии описаны в [docs/ui-overhaul.md](docs/ui-overhaul.md). Изменения поведения и следующие этапы описаны в [docs/overhaul.md](docs/overhaul.md).

## Среда разработки

Для инструментов разработки нужны Node.js **18.18+** и совместимый npm (проверено с Node 18.18 / npm 9). Это не требование к встроенному Node.js в Obsidian: плагин загружается самим приложением. Зависимости закреплены в `package-lock.json`.

```sh
npm ci
npm run dev     # watch: main.js и styles.css в корне
# Ctrl+C завершает watch
npm run build   # проверка типов, стили и production main.js
npm run verify  # тесты, проверка типов и production-сборка
```

`verify` запускает строгую проверку TypeScript, регрессионные тесты и сборку. Команды доступны отдельно: `npm run typecheck`, `npm test`, `npm run build`. Тесты не используют облачные аккаунты или пользовательские vault: основные порты подменяются, публикация и компактация журнала также проверяются в настоящем временном каталоге файловой системы.

`npm run bench:state` измеряет объём записи метаданных и время на 100, 500 и 5000 новых файлов, с applied-эффектами и без них. Benchmark использует in-memory порты; он не измеряет скорость настоящего диска, Obsidian или сети.

Сборка следует [официальному sample plugin](https://github.com/obsidianmd/obsidian-sample-plugin): CommonJS `main.js` в корне, ES2021, inline source map только в dev. Модули `obsidian`, Electron, CodeMirror/Lezer и встроенные модули Node остаются внешними. API проверяется по официальному пакету типов `obsidian`; он не включается в bundle. TypeScript закреплён на 5.8.3, типы Node — на ветке 18. Библиотека XML включается в bundle. В этом checkout отсутствует `manifest.json`: готовый установочный пакет не создаётся. Используйте исходный manifest существующего плагина; его ID и минимальную версию Obsidian нужно подтвердить перед выпуском. Для разработки разместите checkout в `<vault>/.obsidian/plugins/<исходный-id>/` рядом с этим manifest и запустите `npm run dev`. Watch пересобирает файл, но не перезагружает плагин в Obsidian автоматически. ES2021 задаёт синтаксис сборки, а не полифиллы браузерных API или обещание поддержки всех старых версий Obsidian.

## Текущие ограничения

- В старом pull pipeline фоновые удаления остаются ограниченными существующими разрешениями. В новом двустороннем Drive-профиле tracked-удаления распространяются автоматически через корзину после установления базового состояния.
- Для pull-подключений Drive, Яндекс.Диска и WebDAV удаления заблокированы: их обход не доказывает полноту снимка. Новый Drive executor использует отдельную проверку конкретного tracked-объекта; 404 и потеря доступа не считаются удалением.
- Ручное удаление из Git/ZIP и замена конфликтующей локальной версии требуют восстановительной копии. Копии `.conflict-*` создаются рядом с исходным файлом и автоматически не удаляются.
- Изменение локальных байтов или настроек после preview блокирует устаревшую операцию. Full проверяет локальное содержимое также при неизменившейся удалённой версии.
- Журнал и скрытое recovery-хранилище находятся в директории плагина. Повреждённое состояние, разрыв цепочки записей или неизвестная версия после сбоя останавливают исполнение. Лимиты: 512 MiB recovery-объектов и 10 000 записей операций. Компактация обычно оставляет два проверенных checkpoint и необходимые event-опоры. Ошибка очистки видна; накопление ограничено до остановки новых записей. Завершённую локальную историю старше 30 дней можно очищать через окно восстановления; payload незавершённого Drive-намерения защищён от этой очистки. Устаревшие manifest namespace и их резервные файлы удаляются по живым ссылкам. Видимые `.conflict-*` автоматически не удаляются. Отдельное управление незавершёнными удалёнными операциями и repair повреждённого состояния остаются следующими этапами.
- Пустые папки автоматически не удаляются.
- Проверки в настоящем Obsidian, на мобильном устройстве и с реальными аккаунтами остаются отдельным этапом. Проходящие тесты ядра не подтверждают готовность production-релиза.

## Vault workspace and profiles

Единое рабочее окно открывает локальный vault независимо от сети. Выбор папок сохраняется при переключении «Весь vault», а незавершённые формы — при переходах и refresh. Подключения настраиваются и просматриваются отдельно; локальную папку или файл можно связать с конкретным удалённым путём и назначить профиль поведения. Назначения принадлежат vault, каждый файл получает один источник. Ошибка одного preview не скрывает остальные источники; общий запуск требует свежих манифестов всех участвующих подключений. Источники можно запускать по очереди через их меню действий; области остальных источников сохраняют своего владельца. [Руководство](docs/file-rules.md) описывает миграцию, наследование, выбор файлов плагинов и ограничения. Планировщик и разрешения на код по умолчанию выключены.

Operational behavior, limits and verification: [synchronization pipeline overhaul](docs/sync-pipeline-overhaul.md).
